title: 'Messages Overview'

The Messages API sends one text to a client on the practice's behalf. On phones that support RCS, the client sees the practice's name, logo and verified badge, plus rich content: cards with images and buttons, carousels, and reply chips. Every message also carries plain `fallback_text`, which Oliver sends as an SMS when RCS isn't available.

Messages appear in the practice's Oliver inbox like any other text, so staff see what was sent and can pick up the client's reply.

<Note>
  **Identifiers.** The `X-Client-Id` header is the practice's id. `recipient.client_id` is a pet owner (an Oliver client). Webhooks call the practice `clinic_id`, the same value as `X-Client-Id`.
</Note>

## How it works

1. **Send**: POST to [`/messages`](/api-reference/messages/create) with a `recipient`, the `fallback_text` and the `content`.
2. **Delivery**: with `channel: "auto"` (the default), Oliver sends RCS when the practice's RCS sender is live and the client's phone supports it, and `fallback_text` as an SMS otherwise. The client gets one or the other, never both.
3. **Status**: follow the message through `sent` → `delivered` → `read` (RCS only) with [`GET /messages/{id}`](/api-reference/messages/show), or pass a `callback_url` to get a [status webhook](/api-reference/messages/status_webhook) on each change.

<Note>
  An RCS message is either a text bubble or a card, never both. Put the key facts in the card itself; see [Writing card text](#writing-card-text).
</Note>

### Sending with cURL

```bash
curl -X POST https://partner-api.getoliver.com/services/core/open_api/v1/messages \
  -H "Authorization: Bearer $OLIVER_TOKEN" \
  -H "X-Client-Id: $PRACTICE_ID" \
  -H "Content-Type: application/json" \
  -d '{
    "recipient": { "client_id": "0b0e5a54-7c1f-4a43-9d4e-2f3c7d0d1a11" },
    "reference_id": "inv-reminder-88412",
    "fallback_text": "Hi! Millie has preventive care due October 21-22. Book here: https://vet.example.com/book",
    "content": {
      "type": "card",
      "card": {
        "title": "Millie'\''s care is due Oct 21-22",
        "description": "Bordetella vaccine, physical exam and ProHeart 6 injection. We'\''ll combine them into one visit when possible.",
        "media_url": "https://cdn.example.com/millie-reminder.png",
        "buttons": [
          { "type": "open_url", "text": "Schedule now", "url": "https://vet.example.com/book" }
        ]
      },
      "suggestions": [
        { "type": "reply", "text": "Book for me" },
        { "type": "reply", "text": "Call me back" }
      ]
    }
  }'
```

## Buttons and suggestions

| `type` | What it does | Also needs |
| --- | --- | --- |
| `open_url` | Opens a web page | `url` (https) |
| `dial` | Calls a number | `phone_number` (E.164, e.g. `+15125550100`) |
| `reply` | Sends its text back as the client's reply, which lands in the practice inbox. To have Oliver's AI answer instead, send the same `content` through [AI Outbound](/api-reference/ai_outbound/overview#rich-openers-rcs). | optional `id` |

Card `buttons` show on the card. `suggestions` show after the message, as a list of taps on iPhone and a row of chips on Android.

## What `fallback_text` is used for

`fallback_text` is required on every message. It's always the SMS the client gets when RCS isn't available, and the copy staff see in the practice's inbox. Over RCS it also does this, by content type:

| `content.type` | What the client sees from `fallback_text` over RCS |
| --- | --- |
| `text` | The message itself. There's no separate body field: write the message in `fallback_text`. |
| `media` | A small grey caption under the image; links in it aren't tappable. |
| `card` | Nothing; the card shows `title` and `description`. |
| `carousel` | Nothing on iPhone; the cards carry the message. |

Write it to stand on its own as an SMS: include any link or phone number the buttons carry.

Calendar and share-location actions aren't supported by our RCS provider; requests that use them return `400`.

## Limits

| Item | Limit |
| --- | --- |
| Buttons per card | 4 |
| Suggestions per message | 11, of which at most 10 can be `reply` |
| Replies per message (buttons and suggestions together) | 10 |
| Suggestions on a carousel | None; put buttons on its cards |
| Cards in a carousel | 2 to 10 |
| Card title | 200 characters |
| Card description | 1,600 characters |
| Button text | 25 characters (20 for `reply`) |
| `fallback_text` | 1,600 characters |

### Writing card text

Phones decide how RCS content looks; the API can't change it. What we saw on an iPhone in October 2026:

**Card text**

- The description shows up to three lines, about 110 characters, then a chevron the client taps to read the rest. Keep it to one short paragraph.
- A line break ends the preview: everything after the first line break is hidden until the card is opened.
- Put the most important fact, such as the due date, in the `title`. A long title wraps in full; a 97-character title showed on three lines.
- A plain `text` message shows in full, with no preview cut-off.
- A card with no `title` shows its text small and grey, so it's easy to miss. Put the call to action in the `title`.
- An image sent as `media` shows `fallback_text` as a small grey caption under it, and a URL in that caption isn't tappable.

**Buttons**

- One link or dial button shows on the card as a tappable button.
- Two or more link or dial buttons, of the same type or mixed, fold into an "Options" menu the client has to open. Give the card one main action and put the phone number in the text.
- Reply suggestions show as separate taps under the message, all 10 when we sent the maximum, whatever else the card has. With replies only, iPhone shows no note under the message.
- Under every message with buttons, iPhone adds a note: "*Practice name* will see actions you select". On a plain `text` message it sits between the link and the reply taps.

**Images and carousels**

- Use one image for every send; the date belongs in the text, not the image. Wide (2:1), square (1:1) and tall (3:4) images all showed uncropped, at full card width; a tall image makes a tall card.
- Each carousel card follows the button rules on its own: two link or dial buttons on a card fold into that card's "Options". A reply button on a carousel card shows as a tap under the carousel.
- A carousel shows as a stack of cards with a "1 of N" counter, each card's link as a tap. Its `fallback_text` isn't shown as an intro line above the cards on iPhone, so put everything the client needs in the cards.

## Statuses

| Status | Meaning |
| --- | --- |
| `pending` | Oliver couldn't confirm the send after a `502`. Retry the POST with the same `reference_id`. Shown only by `GET`; no webhook. |
| `sent` | Handed to the carrier. |
| `failed` | Couldn't be delivered; see `error_code` and `error_message`. Not always final (see below). |
| `delivered` | Reached the client's phone. |
| `read` | The client opened it (RCS only). |
| `suppressed` | Not sent because the client opted out of texts (`opted_out`) or the number can't receive them (`blocked_number`). Final. |

Statuses only move forward, in the order of this table: `pending` → `sent` → `failed` → `delivered` → `read`. `suppressed` is final. `failed` comes before `delivered` because a message that falls back from RCS to SMS can report a delivery error for the RCS attempt and then be delivered by SMS, so don't treat `failed` as final: a later `delivered` or `read` replaces it.

## Sending hours

Messages are sent immediately; Oliver doesn't queue them for later. Send during the practice's sending hours, **8am to 9pm clinic time**, the same window as the practice's own reminders. Outside them the request returns `400` and nothing is sent:

```json
{
  "success": false,
  "message": "Outside the practice's sending hours (8am to 9pm, America/Chicago). Send the message during sending hours.",
  "data": {
    "message": "Outside the practice's sending hours (8am to 9pm, America/Chicago). Send the message during sending hours.",
    "errors": [{ "field": null, "message": "Outside the practice's sending hours (8am to 9pm, America/Chicago). Send the message during sending hours." }]
  }
}
```

## Errors that mean nothing was sent

| Response | Cause | What to do |
| --- | --- | --- |
| `400`, field `channel` | `channel: "rcs"` at a practice whose RCS sender isn't live yet | Use `auto` (RCS when possible, else SMS) or `sms`. |
| `400`, field `recipient` | The number can't receive texts | Check the number. |
| `400`, field `content` | The messaging provider rejected the content, e.g. an image URL it couldn't fetch | Fix the content. |
| `400`, field `null` | Outside sending hours | Send during sending hours. |
| `502` | The messaging provider was briefly unavailable | Retry with the same `reference_id`. Until you do, `GET` shows the message as `pending`. |

A `400` stores nothing, so you can fix the request and reuse its `reference_id`.

## Opt-outs

Clients who replied STOP are never texted. The response is `200` with `status: "suppressed"` and no text is sent.

The first message Oliver sends to a number at a practice ends with "Reply STOP at any time to unsubscribe." Oliver adds it to `fallback_text` when the message goes out as SMS, and to a plain `text` message without suggestions. Cards, carousels, images and text with suggestions never show it over RCS.

## Idempotency

Set `reference_id` to a unique value per message. Re-sending the same `reference_id` returns the existing message instead of texting the client again, so retries are safe, including after a `502` or a timeout. `reference_id` is echoed in every response and webhook.

## Rate limits

Each practice is limited to **120 messages per minute**. Exceeding the limit returns `429 Too Many Requests`.
